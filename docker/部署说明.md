# 服务器部署

## 普通生产部署

服务器只需 Docker 与 Docker Compose v2。准备后端及同级 `go-zero-admin-vben` 的完整源码，后端 `docker/deploy-compose.yml` 在 Docker 内构建 Go 服务和 Node/pnpm 前端。前端使用 `scripts/deploy/Dockerfile` 的 `production` 目标，宿主机无需 Go、Node 或 pnpm。以下命令均在后端根目录执行。

首次从 [环境模板](deploy.env.template) 创建配置；已有配置须保留：

```sh
cp docker/deploy.env.template docker/.env.deploy
chmod 600 docker/.env.deploy
```

编辑 `docker/.env.deploy`，替换 MySQL 密码、后台 `JWT_ACCESS_SECRET`、独立的 `APP_JWT_ACCESS_SECRET`、RPC App/Token 和默认重置密码等占位值。两个 JWT 密钥须不同且至少 32 字节；API 与业务 RPC 的同类密钥保持一致。`DEFAULT_USER_PASSWORD` 只影响重置密码，不修改 SQL 的初始 `admin / 123456`；正式开放前修改初始账号密码。实际环境文件不提交、不上传到公开源码包，也不复制进镜像。OSS、SMTP 和模型 Key 为可选项；SMTP 使用隐式 TLS。

默认 `FRONTEND_CONTEXT=../../go-zero-admin-vben`，路径相对 `docker/`；若前端目录不同，在环境文件中设置其绝对路径或相对 `docker/` 的路径。必须保留完整前端工作区、锁文件、后端 `pkg/`、`data/db/` SQL 与 `data/api/generated/`；`data/scripts/` 中的生成和检查工具是可选开发入口。两仓库的 `.dockerignore` 会排除依赖、产物和私有配置；分发源码前仍需检查包内容，不能只复制后端应用或前端 `apps/`。

先校验配置并启动依赖：

```sh
docker compose --env-file docker/.env.deploy -f docker/deploy-compose.yml config --quiet
docker compose --env-file docker/.env.deploy -f docker/deploy-compose.yml up -d --wait mysql redis etcd
```

App 注册会保存客户端 IP，并在管理页面展示；注册、登录和验证码请求按客户端 IP 限流。`APP_TRUSTED_PROXY_CIDRS` 优先填写实际反向代理容器的单个 IP，IPv4 加 `/32`、IPv6 加 `/128`，多个用逗号分隔。首次可保留空值启动；完成下文服务启动后，按实际 `web` 容器获取与 API 通信的网络 IP，再更新配置。以下分两步执行，PowerShell 和 sh 均适用：

```sh
docker compose --env-file docker/.env.deploy -f docker/deploy-compose.yml ps -q web
# 将上一步输出的容器 ID 代入，选择该容器与 API 通信的网络 IP
docker inspect <容器ID> --format '{{range .NetworkSettings.Networks}}{{println .IPAddress}}{{end}}'
```

将确认后的地址加 `/32` 写入 `docker/.env.deploy`，再运行 `docker compose --env-file docker/.env.deploy -f docker/deploy-compose.yml up -d --no-deps api` 重新创建 API。使用 Swagger 或其他受控网关时，同样查询相应代理容器的实际地址；本地根 Compose 可将第一条命令换成 `docker compose ps -q swagger-ui`。不要信任整个 Docker 子网、宿主/NAT 网关、客户端地址范围或 `0.0.0.0/0`、`::/0`，否则直连请求可能借伪造转发头绕过 IP 限流。容器重建后 IP 可能变化，须重新确认配置；外部入口也应正确维护实际代理链。空值表示忽略转发头，同一代理后的客户端共用代理 IP 的限额。

确认配置选中的数据库为空后，手动导入唯一全量 SQL，再构建启动后端和页面：

```sh
docker compose --env-file docker/.env.deploy -f docker/deploy-compose.yml cp data/db/gozero-admin.sql mysql:/tmp/gozero-admin.sql
docker compose --env-file docker/.env.deploy -f docker/deploy-compose.yml exec -T mysql sh -c 'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysql --user=root --database="$MYSQL_DATABASE" < /tmp/gozero-admin.sql'
docker compose --env-file docker/.env.deploy -f docker/deploy-compose.yml up -d --build --wait rpc ai-rpc api web
docker compose --env-file docker/.env.deploy -f docker/deploy-compose.yml ps
curl -i http://127.0.0.1:8080/healthz
curl -i http://127.0.0.1:8080/api/v1/sys/randomImage
```

部署 Compose 不自动导入 SQL；已有数据库不能重放全量 SQL。全量 SQL 已含当前迁移，使用容器的 `MYSQL_DATABASE` 和 `MYSQL_ROOT_PASSWORD`，无需将凭据写进命令。Windows 可使用相同 Compose 命令。

页面默认监听 `WEB_PORT=127.0.0.1:8080`，容器内 Nginx 将 `/api/` 转发到 `http://api:7001/` 并去掉前缀，保留 `/v1/sys`、`/v1/ai` 或 `/v1/app`。默认 hash 路由，静态站点也提供 `index.html` 回退。生产镜像不使用 Vite 开发代理。API 默认仅绑定 `API_PORT=127.0.0.1:7001`，MySQL、Redis、etcd 和 RPC `6001/6002` 不发布宿主端口。对外站点由服务器 HTTPS 入口转发到本机 `8080`；按实际入口配置域名和证书。

Swagger 按需启动，默认仅监听 `127.0.0.1:8081`，与页面端口分开：

```sh
docker compose --env-file docker/.env.deploy -f docker/deploy-compose.yml up -d --wait swagger-ui
```

管理文档为 `http://127.0.0.1:8081/`，App 文档为 `http://127.0.0.1:8081/?audience=app`。本机根 Compose 对应端口为 `7000`。同一个 `gen.ps1 swagger` 产出两份 JSON；管理文档现有 92 个接口，App 文档 12 个，App 接口不参与后台 API 权限同步。

### 升级与停止

先更新配套的前后端源码并保留 `docker/.env.deploy`。维护窗口中停止三个写库服务，保留 MySQL 运行；仅停止 API 或业务 RPC 会遗漏仍在写库的 AI 后台：

```sh
docker compose --env-file docker/.env.deploy -f docker/deploy-compose.yml stop api ai-rpc rpc
```

使用 MySQL 客户端连接部署环境的实际业务库，手工完成维护：

1. 导出完整备份并核验完整性及可恢复性。保存在 `data/db/backups/`，SQL 备份及配套 SHA256 校验文件纳入 Git，Docker 构建上下文仍排除该目录。仓库历史备份按文件名中的快照时间手工保留最新两份，配套校验文件同存；初始化 SQL 和增量迁移不参与备份轮替。
2. 对照 `schema_migrations` 的 `filename` / `checksum` 与 `data/db/migrations/`，按文件名顺序只执行未应用迁移。已应用文件的校验和不符时停止；历史记录缺失时先核实实际结构，不直接重跑。现有库不会由 Docker 自动升级，也不能重放全量初始化 SQL。
3. 客户端遇到 SQL 错误须立即停止，不继续后续语句或迁移，不登记失败项；核实部分执行状态后再处理。每个文件完整成功后维护 `filename`、`checksum` 和 `applied_at`；SHA-256 按 UTF-8 去 BOM、CRLF 转 LF 后的文件内容计算，保存为 64 位小写十六进制。

App 模块先执行 `data/db/migrations/20261019_app_members.sql`，新增五张独立 App 表、VIP 方案以及 2 个菜单、5 个按钮和 8 个后台 API 资源；随后执行 `20261019_app_registration_ip.sql`，增加注册 IP 与归属地字段。已应用 members 迁移的环境只应用后者，不能修改旧迁移或替换其已登记校验和；旧账号新增字段保持空值，原数据保留。两份迁移均不授予现有角色权限。需要角色 1 管理该模块时，在服务仍停止的维护窗口明确执行 `data/db/operator/20261019_app_member_admin_bootstrap.sql`；其他角色通过现有权限编辑器授权。新库全量 SQL 已包含两份迁移及初始化授权，已有库不得因此重放全量 SQL。

核验结构、数据和迁移记录后，再构建启动并检查日志：

```sh
docker compose --env-file docker/.env.deploy -f docker/deploy-compose.yml up -d --build --wait rpc ai-rpc api web
docker compose --env-file docker/.env.deploy -f docker/deploy-compose.yml logs --tail=100 api ai-rpc rpc web
```

日常停止使用 `docker compose --env-file docker/.env.deploy -f docker/deploy-compose.yml stop`，保留数据卷。不要添加 `down -v`。此 Compose 的数据卷与本地开发分开，本次调整不改变既有卷策略。

本地仍在后端根目录运行 `docker compose up -d --build --wait`，前端同级目录运行 `pnpm dev`（`5999`）；根 Compose 的新 MySQL 卷自动导入 SQL，API 为 `7001`，Swagger 为 `7000`。详见 [README](../README.md#快速开始)。

### 服务与模型配置

App 账号通过邮箱或手机号加密码注册，人工审核通过后才能登录；账号审核和会员开通是两个操作。后台管理员仍使用 `sys_users`，App 使用 `app_users`、`app_user_identities`、`app_sessions`、`app_membership_plans`、`app_membership_grants`。App 访问令牌默认 `APP_JWT_ACCESS_EXPIRE=900` 秒，刷新令牌默认 `APP_JWT_REFRESH_EXPIRE=2592000` 秒；刷新会轮换并检测复用，禁用或撤销设备立即影响后续认证，恢复账号不恢复旧会话。会员按当前授予记录的有效期判断，禁用账号不暂停会员计时。

注册归属地来源为 ip2region 离线数据库，`rpc.yaml.template` 的 `IPLocation.IPv4Path` / `IPv6Path` 指向 `data/ipregion/ip2region_v4.xdb` / `ip2region_v6.xdb`。部署包须保留对应数据文件，离线库加载和容器实际查询已验证；无需向外部定位服务发送用户 IP。注册 IP 与归属地保存到账号记录，旧账号迁移后保持空值。

邮件复用现有 Mail RPC，App 注册使用独立 `app_register` 验证码场景。同一客户端 IP、同一邮箱每天各最多请求 5 次验证码，按 `Asia/Shanghai` 自然日计数。`APP_EMAIL_VERIFICATION_REQUIRED=false` 为默认值；设为 `true` 后邮箱注册必须提交 5 分钟内有效的一次性验证码，验证成功仍需管理员审核。手机号首版人工核实。SMTP 的 `SMTP_HOST`、`SMTP_PORT`（默认 465）、`SMTP_USER`、`SMTP_PASSWORD`、`SMTP_FROM` 只注入业务 `rpc` 并渲染到 `rpc.yaml.template`，API 和前端不需要 SMTP 凭据。默认关闭强制验证时，无 SMTP 也能启动和注册；启用后须验证 `GET /v1/app/auth/options`、验证码发送和实际邮箱收信，再开放注册。当前仓库测试尚未验证真实 SMTP 投递。

当前 AI 服务依赖同一业务库：`sys_users` 用户行锁用于提交并发限制，任务提交/取消与 `sys_audit_logs` 审计在同一事务中完成。新部署导入完整 `data/db/gozero-admin.sql`，不只创建 AI 三张表；已有库只按迁移记录升级。

本机完整后端使用根目录 `docker-compose.yml`；服务器部署使用 `docker/deploy-compose.yml`，数据卷独立。两个流程的应用容器均从 `docker/*.yaml.template` 构建配置模板，入口通过 `envsubst` 生成 `/tmp/config.yaml`，不读取 `application/.../etc/` 下的本机 YAML。打包必须包含 `pkg/`、`data/db/` SQL 和完整 `data/api/generated/`；更新接口后先生成 Swagger，再构建 RPC。

AI 普通模型参数填写 `docker/ai-rpc.yaml.template` 的 `AI` 块，直接设置 `Enabled`、`Provider`、执行限制和 `DeepSeek` / `Qwen` 的 `Model`、`BaseURL`，不通过环境变量替换。AI 默认 `Enabled: false`；实际运行设置为 `true`，选择 `deepseek` 或 `qwen`，填写支持 function calling 的模型及可达 endpoint。Qwen endpoint 必须匹配账号区域。当前用户还需 AI 菜单、按钮和 API 权限；AI 工具通过业务 RPC 校验业务权限。

模型环境仅保留 `API_KEY_DEEPSEEK` 和 `API_KEY_QWEN`，实际值填入 `docker/.env.deploy`，通过 `--env-file` 只注入 `ai-rpc` 容器。AI RPC 只读取所选提供商的固定 Key，YAML 不保存 API Key；业务 `rpc` 和 `api` 不接收模型 Key。旧 `AI_AGENT_*`、`*_MODEL`、`*_BASE_URL` 不再生效，升级时将相应非密钥值迁移到 YAML 并移除旧环境字段。

修改 YAML 模板或 Key 后，在后端根目录执行：

```sh
docker compose --env-file docker/.env.deploy -f docker/deploy-compose.yml up -d --build --no-deps ai-rpc
```

YAML 模板随镜像构建复制，此命令构建并重新创建 AI RPC；单纯 `restart` 不更新容器环境。容器不使用本机 `application/ai/rpc/etc/ai.yaml` 或其中的 `APIKey` 兜底。根 Compose 的两个 Key 显式为空，本机启用时还需只在 `ai-rpc.environment` 中为所选 Key 配置环境变量引用，将实际值放入忽略的根目录 `.env`，再重建 AI RPC，详见 [AI 助手](../README.md#ai-助手)。源码或数据库整体升级需按上文停止三个服务再操作。实际密钥文件限制访问权限；密钥文件已从 Docker 构建上下文排除。

部署环境必须填写 `RPC_AUTH_TOKEN`（至少 32 字节的随机密钥）和 `RPC_AUTH_APP`；API → 两个 RPC、AI RPC → 业务 RPC 复用同一组值。业务 RPC 在 Redis 的 `go-zero-admin:rpc:tokens` 哈希登记凭据，AI RPC 使用独立的 `go-zero-admin:ai-rpc:tokens`；两个服务均启用 go-zero 内置 `Auth` 与 `StrictControl`。Redis 故障时拒绝未验证调用；注册失败或与已登记密钥冲突时服务停止启动，日志不会输出密钥。本机根 Compose 同样启用 RPC 认证，两个 RPC 在容器内监听 `0.0.0.0:6001`、`0.0.0.0:6002`，不向宿主机发布端口。API 通过 `AppletRPC`（etcd 键 `applet.rpc`）和 `AIRPC`（键 `ai.rpc`）连接下游，AI 的 `AppletRPC` 调用业务工具。

轮换 RPC 密钥时先停止全部 API、AI RPC、业务 RPC 实例，在同一 Redis 中删除上述两个认证哈希下对应应用字段，更新所有实例的环境配置，再统一启动。内置鉴权缓存最长五分钟，因此停止旧实例是轮换步骤的一部分。不要让不同凭据的副本相互覆盖。

首次全量 SQL 已包含权限版本结构；旧库升级需在启动 RPC 前应用相应未登记迁移。权限变更与持久化版本递增同事务提交；每个实例通过定时检查、Redis 通知及鉴权请求前的版本检查补偿丢失消息。数据库无法检查当前版本时鉴权失败，数据库恢复后自动重载；进程退出会关闭同步工作线程与订阅连接。

2026-10-20 的本地验收已完成两个 App 增量迁移、备份恢复验证、Docker 最终重建及七服务健康检查，原有 18 个后台用户保持不变；生产 Compose 模板通过 `config --quiet` 校验。HTTP 已验证 App 业务闭环及注册 IP/归属地，直接访问 API 或经 Nginx 伪造转发头均未改变记录的客户端 IP。此记录不代表已部署远程生产环境；真实 SMTP 投递与管理页面的浏览器审核/VIP 点击闭环仍未验收。
