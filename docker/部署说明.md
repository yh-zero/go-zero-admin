# 服务器部署

## 公开只读演示（本次云部署）

前后端分别维护。在后端根目录运行下列命令，在本机编译 Linux amd64 后端和演示前端；服务器不需要 Go/Node 编译环境：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File test/sh/package-demo.ps1
```

包输出至 `bin/cloud-releases/<发布号>/go-zero-admin-demo-linux-amd64.tar.gz`，同目录附 SHA256 摘要；不含本机密钥、Git、依赖缓存和数据库备份。将下面的 `<发布号>` 替换为生成的目录名。通过已配置的 SSH 上传：

```powershell
ssh root@175.178.67.80 'mkdir -p /yanghao/gozeroadmin/uploads'
scp bin/cloud-releases/<发布号>/go-zero-admin-demo-linux-amd64.tar.gz root@175.178.67.80:/yanghao/gozeroadmin/uploads/<发布号>.tar.gz
ssh root@175.178.67.80
```

登录服务器后执行；先用 `sha256sum` 对照本机摘要，确认一致再继续：

```sh
cd /yanghao/gozeroadmin
sha256sum uploads/<发布号>.tar.gz
mkdir -p releases/<发布号>
tar -xzf uploads/<发布号>.tar.gz -C releases/<发布号>
cd releases/<发布号>/backend
sh docker/demo.sh prepare /yanghao/gozeroadmin yh9527.top 175.178.67.80
sh docker/demo.sh init
sh docker/demo.sh start
```

要求 Docker Compose 与 Python 3.12/libcrypt bcrypt，本次为 Ubuntu 24.04/x86_64。首次只用于空的独立演示库，`init` 会应用完整迁移、备份并执行一次演示种子；重复执行保留数据与凭据，未知业务数据拒绝改写。已有站点更新时先执行旧发布的 `stop` 与 `backup`，再运行新发布的初始化命令。

站点为 `https://yh9527.top` / `http://175.178.67.80`，访客 `admin / 123456`，仍使用真实图片验证码。公网只开放80/443，API仅本机7001，数据库和RPC不开放；域名解析正确且80/443可达后，Caddy自动签发/续期HTTPS证书。

`runtime/` 在授权项目目录内保存数据库、缓存、注册中心及证书；`.env.demo` 与 `ADMIN_CREDENTIALS.txt` 为0600。私有维护账号为 `demo-maintainer`，角色1使用服务器随机密码；公开 `admin` 固定使用普通只读角色9527，用户名不授予管理权限。初始化停用旧示例账号。代理封闭写操作、改密、退出、设备及审计隐私入口；前端退出只清当前浏览器。启动检查拒绝公开账号升权、额外API/按钮权限及角色继承。AI服务部署但 `Enabled:false`、Key强制为空，不能发起模型任务。

旧版 `demo / Demo@2026` 演示环境升级前先停止应用服务并备份；新版 `init` 对已完成标记的旧环境执行一次公开登录迁移，保留用户ID、菜单/API授权、私有密码和业务数据，并使旧会话失效。也可在已备份的旧环境运行 `python3 docker/demo-bootstrap.py public-login`；新账号布局下重复执行只检查，不重设密码。

日常在当前发布后端目录运行 `sh docker/demo.sh status`；停止与备份为 `sh docker/demo.sh stop`、`sh docker/demo.sh backup`。更新先停止旧发布并备份，再解压新发布，运行新的 `prepare → init → start`，保留同一 `runtime/` 和Compose项目名。不得执行 `down -v`、清库或重放已有库基线；数据库跨大版本升级另行评估。

跳过的高风险事项与验收状态见 [根目录部署记录](../CLOUD_DEPLOYMENT_NOTES.md)。完整生产环境与公开演示的权限用途不同，参考下方维护说明。

服务故障先尝试上述 `start`；需要完整新系统时使用 [根目录快速恢复说明](../QUICK_RECOVERY.md) 和 `docker/demo-rebuild.py`。工具校验发布包后准备独立项目和空数据库，生成切换/回退命令，不删除旧库，也不自动切换线上入口。

<summary>普通生产部署、升级与模型配置</summary>

完整部署步骤统一维护在 [README：服务器部署](../README.md#服务器部署)，包括源码打包、环境配置、数据库迁移、前端发布、升级与停止；请以该文档为准。

在后端根目录执行。首次准备完整源码及 `docker/.env.deploy` 后，Linux 最短启动流程为：

```sh
docker compose --env-file docker/.env.deploy -f docker/deploy-compose.yml config --quiet
sh test/sh/db.sh init deploy
docker compose --env-file docker/.env.deploy -f docker/deploy-compose.yml up -d --build
docker compose --env-file docker/.env.deploy -f docker/deploy-compose.yml ps
```

`init deploy` 启动 MySQL、Redis、etcd 依赖，备份并执行未应用迁移，不启动 API、业务 RPC 或 AI RPC。Windows 对应 `powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\test\sh\db.ps1 -Action Init -Environment Deploy`。根目录 `docker-compose.yml` 仍只提供本机依赖；本机三个后端服务使用 `test/sh/dev.ps1` 或各自 Go 入口启动。

部署后端包含三个服务：`rpc`（`applet-rpc`，内部 `6001`）、`ai-rpc`（`applet-ai-rpc`，内部 `6002`）、`api`（`applet-api`，原 `7001`）。API和AI RPC分别依赖业务RPC，API启动不依赖AI；默认`up`构建并启动三服务。前端仍通过原API访问 `/v1/sys` 和 `/v1/ai`，不新增HTTP端口，两个RPC均未向宿主机发布端口。

升级时先停止 API 入口，再停止 AI 后台和业务 RPC；三个服务全部停止后才备份、迁移，随后构建并启动新版本。仅停止 API/业务 RPC 会遗漏仍在写库的 AI 后台。维护窗口中的对应命令为：

```sh
docker compose --env-file docker/.env.deploy -f docker/deploy-compose.yml stop api ai-rpc rpc
sh test/sh/db.sh backup deploy
sh test/sh/db.sh status deploy
sh test/sh/db.sh migrate deploy
docker compose --env-file docker/.env.deploy -f docker/deploy-compose.yml up -d --build
docker compose --env-file docker/.env.deploy -f docker/deploy-compose.yml logs --tail=100 api ai-rpc rpc
```

独立 AI RPC 拆分没有新增迁移，继续复用 `20261003_zz_ai_agent.sql` 的 `sys_ai_conversations`、`sys_ai_runs`、`sys_ai_messages` 三表。当前 AI 服务依赖同一业务库：`sys_users` 用户行锁用于提交并发限制，任务提交/取消与 `sys_audit_logs` 审计在同一事务中完成。新部署应应用完整迁移链，不只创建 AI 三表，也不重新导入已有库的基线 SQL。

开发依赖使用根目录 `docker-compose.yml`；部署使用 `docker/deploy-compose.yml`，数据卷独立。打包必须包含 `pkg/`、数据库脚本、`test/sh/` 和完整 `data/api/generated/`；更新接口后先生成 Swagger，再构建 RPC。

AI 普通模型参数填写 `docker/ai-rpc.yaml.template` 的 `AI` 块，直接设置 `Enabled`、`Provider`、执行限制和 `DeepSeek` / `Qwen` 的 `Model`、`BaseURL`，不通过环境变量替换。AI 默认 `Enabled: false`；实际运行设置为 `true`，选择 `deepseek` 或 `qwen`，填写支持 function calling 的模型及可达 endpoint。Qwen endpoint 必须匹配账号区域。当前用户还需 AI 菜单、按钮和 API 权限；AI 工具通过业务 RPC 校验业务权限。

模型环境仅保留 `DEEPSEEK_API_KEY` 和 `QWEN_API_KEY`，实际值填入 `docker/.env.deploy`，通过 `--env-file` 只注入 `ai-rpc` 容器。AI RPC 只读取所选提供商的固定 Key，YAML 不保存 API Key；业务 `rpc` 和 `api` 不接收模型 Key。旧 `AI_AGENT_*`、`*_MODEL`、`*_BASE_URL` 不再生效，升级时将相应非密钥值迁移到 YAML 并移除旧环境字段。

修改 YAML 模板或 Key 后，在后端根目录执行：

```sh
docker compose --env-file docker/.env.deploy -f docker/deploy-compose.yml up -d --build --no-deps ai-rpc
```

YAML 模板随镜像构建复制，此命令构建并重新创建 AI RPC；单纯 `restart` 不更新容器环境。本机普通参数在 `application/ai/rpc/etc/ai.yaml`，`.env.local` 仅存两个 Key，由 `test/sh/dev.ps1` 的 Start/Restart 加载；已有非空进程 Key 优先，退出后恢复，不自动同步到容器。Key 只给独立 AI 子进程，业务 RPC/API/构建/数据库子进程均屏蔽。源码或数据库整体升级需按上文停止三个服务再操作。实际密钥文件限制访问权限，模板保持空密钥；密钥文件已从 Docker 构建上下文排除。详见 [AI 本机配置与运行边界](../README.md#ai-agent-本机配置)。

部署环境必须填写 `RPC_AUTH_TOKEN`（至少 32 字节的随机密钥）和 `RPC_AUTH_APP`；API → 两个 RPC、AI RPC → 业务 RPC 复用同一组值。业务 RPC 在 Redis 的 `go-zero-admin:rpc:tokens` 哈希登记凭据，AI RPC 使用独立的 `go-zero-admin:ai-rpc:tokens`；两个服务均启用 go-zero 内置 `Auth` 与 `StrictControl`。Redis 故障时拒绝未验证调用；注册失败或与已登记密钥冲突时服务停止启动，日志不会输出密钥。本机开发两个 RPC 分别监听 `127.0.0.1:6001`、`127.0.0.1:6002`；改成非回环地址必须启用认证。API 通过 `AppletRPC`（etcd 键 `applet.rpc`）和 `AIRPC`（键 `ai.rpc`）连接下游，AI 的 `AppletRPC` 调用业务工具。

轮换 RPC 密钥时先停止全部 API、AI RPC、业务 RPC 实例，在同一 Redis 中删除上述两个认证哈希下对应应用字段，更新所有实例的环境配置，再统一启动。内置鉴权缓存最长五分钟，因此停止旧实例是轮换步骤的一部分。不要让不同凭据的副本相互覆盖。

迁移 `20261002_00_policy_sync.sql` 必须在新版 RPC 启动前执行。权限变更与持久化版本递增同事务提交；每个实例通过定时检查、Redis 通知及鉴权请求前的版本检查补偿丢失消息。数据库无法检查当前版本时鉴权失败，数据库恢复后自动重载；进程退出会关闭同步工作线程与订阅连接。
