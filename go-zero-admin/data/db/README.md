# 数据库初始化与升级

`gozero-admin.sql` 是仅供空库使用的完整初始化文件，由历史基线、迁移、管理员初始化脚本和 fresh-only 示例数据生成。已有数据库只应用尚未执行的增量迁移；更新初始化文件不会修改已有数据卷。

## 数据库文件

| 路径 | 用途 |
|---|---|
| `gozero-admin.sql` | 生成的空库初始化 SQL，包含最终表结构和完整可体验的演示数据。不要手工编辑，也不要导入已有业务库 |
| `baseline.sql` | 历史基线，保留早期结构、数据和迁移记录，供生成初始化文件使用 |
| `migrations/` | 已有库的增量迁移，按文件名顺序执行；成功后在 `schema_migrations` 登记校验和 |
| `operator/` | 可选管理员授权等运维脚本，已有库需在维护窗口显式执行；不会随增量迁移自动授权 |
| `seeds/demo.sql` | 仅供全新安装的账号、组织、菜单、权限、会员、文件资源及引用示例，由生成器在历史脚本之后追加，不属于已有库升级流程 |
| `seeds/activity.sql` | 全新安装的审计和 AI 演示记录，紧随 `demo.sql` 追加；不包含有效登录会话 |
| `backups/` | 仓库只提供最新可公开演示库快照 `gozero-admin-demo-latest.sql` 及配套 `.sha256`，不属于 fresh 输入；部署时产生的其他备份默认被 Git 忽略，不应提交 |
| `*_test.go` | 初始化 SQL 的生成一致性、迁移校验和及真实 MySQL 导入等守卫测试 |

`baseline.sql`、已发布迁移和 `operator/` 的历史内容保持兼容。演示数据由 `seeds/demo.sql` 和 `seeds/activity.sql` 在生成文件尾部完成，不通过改写历史迁移来清理已有业务数据。

## 生成与导入空库

在后端仓库根目录执行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File data/scripts/build-fresh-sql.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File data/scripts/build-fresh-sql.ps1 -Check
```

生成器按固定顺序拼接 `baseline.sql`、尾部迁移与管理员初始化脚本，最后依次追加 `seeds/demo.sql`、`seeds/activity.sql`。迁移的 SHA-256 校验和由生成器计算；这两份示例 seed 不作为增量迁移登记，也不能单独在已有库执行。

本地根 Compose 的新 MySQL 数据卷会自动执行 `gozero-admin.sql` 一次：

```powershell
docker compose up -d --build --wait
docker compose ps
```

服务器使用独立部署编排，通过 `./docker/deploy.sh import` 导入空库，完整步骤见 [部署说明](../../docker/部署说明.md)。该命令拒绝向非空库导入。空库检查只防止误覆盖，不能用于判断数据库版本。

更新源码或重新生成初始化文件后，已有数据卷仍保持原状。不要为了同步新示例数据而重放完整 SQL。

## 已有库升级

1. 停止所有写库服务，保留 MySQL 运行；导出业务库完整备份并检查备份可恢复。
2. 核对 `schema_migrations` 的 `filename`、`checksum` 与 `migrations/` 文件，按文件名顺序执行尚未应用的迁移。已应用文件校验和不符时先核实原因，不直接重跑。
3. SQL 执行失败时立即停止，不继续后续迁移，也不登记失败文件；先检查可能已经执行的语句。每个文件完整成功后，登记 `filename`、`checksum` 和 `applied_at`。
4. 如需给管理员开放新增功能，在维护窗口显式执行对应 `operator/` 脚本。其他角色通过权限编辑器按需授权。
5. 核验结构、迁移记录及关键业务数据，再启动服务并检查健康状态。

`checksum` 为文件按 UTF-8 去 BOM、将 CRLF 转为 LF 后计算的 SHA-256，使用 64 位小写十六进制。已被环境应用的迁移文件不可修改。

2026-10-03 及更早迁移已经合并进 `baseline.sql`，独立文件已移除，其 `schema_migrations` 记录保留为历史事实。2026-10-07 之前部署的库不再提供完整升级文件，需要时应从 Git 历史取回并核实升级路径。

可使用服务器脚本的 `migrate-check` 只读核对迁移，使用 `upgrade` 完成停写、备份、逐项确认迁移及重启。已有库升级不会执行 `seeds/demo.sql` 或 `seeds/activity.sql`，不会重置账号、角色或历史业务数据。

## 备份与开发库重置

仓库提供的 `data/db/backups/` 只保留最新可公开演示快照 `gozero-admin-demo-latest.sql` 及其 `.sha256`。该快照来自干净的演示数据库，供查看或恢复演示环境，不参与 `gozero-admin.sql` 生成；正常全新安装仍使用生成的初始化 SQL。

部署脚本仍可向 `data/db/backups/` 写入私有业务备份；除白名单中的公开演示快照外，其他 SQL 和校验文件由 Git 忽略，不能提交。本机整理前的历史私有备份归档在 Git 忽略的 `.cache/db-backup-archive/`，仅用于本机回退，不作为生产备份方案。生产业务备份须按部署方策略保存在受控位置，核验可恢复性，并单独备份 RustFS 对象数据及配置；不要把真实账号、令牌、业务记录或模型密钥加入公开演示快照。

正常停止使用 `docker compose down`，数据卷会保留。需要重置开发库时，先确认目标 Compose 项目、业务库和对应 MySQL 卷，保存并核验数据库备份，再明确执行重置。删除卷属于有损操作，不作为升级或版本检查步骤，也不要连带删除 Redis、RustFS 等其他服务的数据卷。

判断升级状态应核对迁移文件、校验和与实际字段，不能通过比较表数量判断版本：字段、索引和权限变化都可能不增加表。

## 维护与验证

新增结构或数据升级时，在 `migrations/` 创建新文件；需要可选授权时另建 `operator/` 文件，并在 `data/scripts/build-fresh-sql.ps1` 中维护顺序。只影响全新安装的账号、菜单排序和文件示例写入 `seeds/demo.sql`，审计与 AI 演示记录写入 `seeds/activity.sql`。修改后重新生成 `gozero-admin.sql`，不要直接修改生成结果。

生成一致性可使用 `build-fresh-sql.ps1 -Check` 检查。涉及 fresh seed 时，在隔离的空 MySQL 数据库导入一次，核对迁移记录、四个后台账号的权限与停用边界、六个 App 账号的状态、三条 VIP 授予、真实文件对象及引用保护、内置审计和 AI 历史展示；不要在业务库执行示例 seed 来验证。
